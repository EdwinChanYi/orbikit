# Design: orbikit 服务骨架 skill

Generated by /office-hours on 2026-11-12

Status: APPROVED

## Problem Statement

orbikit 要给没有后端思维的人一条路：产品经理或前端工程师描述需求，AI 在这个框架上做出高并发、高可用的后端。这次只定框架。用户自己的话是：「不会加其他了，先把框架定好就行，具体开发再来。」10 倍好的版本是：「测试好服务可以正常运行。」

语音直播、房间消息、礼物、私聊、榜单、玩法是以后的例子，不是这份设计要做的功能。

## What Makes This Cool

和普通「让 AI 写代码」的差别，是生成每个服务的基础代码框架，而且这个框架长在已经跑起来的 orbikit 上。用户确认过这句：「将各个服务的基础代码框架生成。」skill 的顺序是用户定的：「先思考这些服务需要怎么拆分不同的微服务，第二步给这些服务定义接口，如果有不清楚的，可以询问用户具体的问题；第三步，创建服务所需要的基础。」

## Constraints

- 使用者是产品经理或前端工程师。他们不选择 Kafka、etcd 或进程怎么部署。
- 这次不实现礼物、私聊、榜单、玩法，也不写「增加某个服务功能」的 skill。那个 skill 留空位，以后再定。
- 高并发、高可用指沿用现成的 gRPC、etcd 注册、yaml 配置和 compose。不为每个需求新发明一套架构。
- 完成标准是进程能启动并通过测试。双实例、杀掉一个再验证调用，不作为这次的完成标准。
- 需求不清楚就问。接口列表确认之前，不生成 proto，不生成服务代码。
- 分发是公开仓库里的 markdown skill。不新增二进制，不新增包管理器。
- 不改旧公司仓库。不在这次提交或打版本标签。

## Premises

1. 第一组 skill 不实现礼物、私聊、榜单、玩法。它只拆服务、跟用户确认接口、按现有服务的样子生成骨架，并用测试证明进程能启动。
2. 高并发、高可用指骨架沿用现成的 gRPC、etcd 注册、配置和 compose，不为每个需求新发明架构。冷读认为「进程能启动」证明不了故障切换。用户保持这条前提，完成标准仍是服务能启动。
3. 需求不清楚就问。用户确认接口列表之前，不生成服务代码。

## Cross-Model Perspective

Codex 未安装（`CODEX_MODE: not_installed`）。下面是同一次环境里的冷读，不是外部模型，分量要打折。

冷读认为更酷的版本是：从现有 gateway 的 WebSocket 打到新服务，起两个实例，杀掉一个，下一次调用落到还活着的那个。它引用的兴奋点是：「给产品经理或者前端工程师。描述下需求就能完成后端服务高并发高可用的代码。」它认为 Go Micro 已经覆盖「生成并跑起来」，orbikit 要补的是自己的形状：`/orbikit/services/<name>/<instance>`、listen 之后再 Bind、调用走 `DialDiscovered`、本地配置直连、部署配置走 etcd。它建议的周末原型是一份已确认的最小 API 夹具，外加双实例故障测试。它认为第 2 条前提过窄。用户保持了第 2 条，并选择了完整三步，没有选择「先做夹具」。

## Approaches Considered

### Approach A: 一条生成 skill

人先把接口定好，skill 只生成骨架并测到进程能启动。未选：skill 不会在不清楚时提问，拆分留在人身上。

### Approach B: 三步 skill

拆分、确认接口、生成能启动的骨架，加一份编程规范。这是选定的做法，见下一节。

### Approach C: 固定夹具先跑绿

用一份已经确认的最小 API 生成同形服务，测试只证明进程起来，访谈以后再做。未选：第一版没有追问，夹具也不是用户描述需求的那条路。

## Recommended Approach

仓库根目录新增 `skills/`，四份 markdown，外加一份入口。不绑定某一种编辑器。

入口是 `skills/orbikit-extend-service/SKILL.md`。产品经理调用这一份。它按顺序执行下面三步。服务列表和接口列表只存在于同一次入口会话里，不另建仓库文件。确认是用户对这份接口列表的明确同意。仅仅打开某个 skill 不算确认。

`skills/orbikit-define-api/SKILL.md` 和 `skills/orbikit-scaffold-service/SKILL.md` 在没有这句同意时，不写 proto、`api/gen`、`cmd/<service>`、`internal/<service>`、`configs/<service>.yaml`、`deploy/configs/<service>.yaml`、compose 服务项和监听测试。打开 skill 不算同意。

拆分和生成都拒绝不符合 `^[a-z][a-z0-9]*$` 的名字，与现有 `core`、`chatroom`、`webhook`、`gateway` 同一形状。与已有 `cmd` 目录比较时忽略大小写。拆分和生成在正则和忽略大小写的 cmd 重名之外，再拒绝 Go 关键字。拒绝时不写文件，也不覆盖已有服务。关键字是 `break`、`default`、`func`、`interface`、`select`、`case`、`defer`、`go`、`map`、`struct`、`chan`、`else`、`goto`、`package`、`switch`、`const`、`fallthrough`、`if`、`range`、`type`、`continue`、`for`、`import`、`return`、`var`。`echo` 不在其中。`pkg/discovery` 的 `validateService` 只拒绝空名字和包含 `/` 的名字；skill 的规则更严，因为 `package gift-svc` 和 `package 123` 不能通过 `go test`。

1. `skills/orbikit-split-service/SKILL.md`：读需求，输出服务列表。每个服务一行职责。不写代码。
2. `skills/orbikit-define-api/SKILL.md`：为每个服务列接口。有不清楚的点就问具体问题。用户确认列表之后，才在 `api/proto/service/` 写 proto。新 proto 使用与 `api/proto/service/core_service.proto` 相同的 `option go_package = "github.com/EdwinChanYi/orbikit/api/gen/servicepb;servicepb";`。然后按仓库已有顺序生成：先 `make tools`（安装 `buf@v1.34.0`、`protoc-gen-go@v1.34.2`、`protoc-gen-go-grpc@v1.4.0`），再 `make proto`（`buf generate`）。留下 `api/gen` 的结果。仓库里没有这两个插件的可执行文件，只跑 `buf generate` 不会生成代码。CI 的 proto 检查是安装同样版本之后执行 `buf generate && git diff --exit-code api/gen`。只提交 proto、不留下生成代码时，这条检查会失败。
3. `skills/orbikit-scaffold-service/SKILL.md`：为每个已确认的服务生成骨架。样板的注册和配置形状来自 `cmd/chatroom`、`cmd/core`、`cmd/webhook`，不是 gateway。gateway 只拨号，不注册。

编程规范是 `skills/orbikit-coding-standard/SKILL.md`。它只描述现成做法，外加下面为了能测到监听而必须说清的启动顺序。新服务必须：

- 生成 `cmd/<service>/main.go`、`internal/<service>` 里的配置和 gRPC server、`configs/<service>.yaml`、`deploy/configs/<service>.yaml`，并在 `deploy/docker-compose.yml` 增加一个 service。compose 项沿用现有 `x-service`、构建参数 `SERVICE` 和 `-config`。`depends_on` 只包含这个骨架真正要连接的基础设施。
- 本地 `configs/<service>.yaml` 使用 `host:port`，不写 `etcd.endpoints`。`deploy/configs/<service>.yaml` 写 `etcd` 和 `register.name`。
- listen 之后调用 `discovery.Bind`。没有出站调用的服务也要 Bind。`DialDiscovered` 只在确认过的接口需要调用其他服务时使用，并且每一条调用写明目标。验收用的 `echo` 不拨号。本地样板的出站地址是 `host:port`，例如 `configs/chatroom.yaml` 的 `core_addr: localhost:9001`，不是 `etcd:///`。`pkg/grpcx` 在目标以 `etcd:///` 开头且 registry 为 nil 时，`DialDiscovered` 会直接返回错误。
- 骨架注册这次生成的 server，按确认过的 proto 调用对应的 Register 函数。不要假定进程名、proto 文件名和 Register 函数三者相同。webhook 进程注册的是 `RegisterMsgCopyServer`，对应文件是 `api/proto/service/msgcopy_service.proto`。
- 这份骨架的启动函数只做五步：加载不写 `etcd.endpoints` 的本地配置、`discovery.Open`、`net.Listen`、`discovery.Bind`、然后 Serve，并在上下文取消后返回。这条路径不调用 `mysqlx.New`、`redisx.New`、`kafkax.NewSyncProducer` 或 `kafkax.NewConsumerGroup`。配置校验不要求 MySQL、Redis 或 Kafka 有值。现有 `internal/chatroom.Validate` 会在这些字段为空时返回错误，现有 main 也在这些客户端返回之后才等待信号。把连接挪到 Listen 之后仍然会让 CI 里的测试失败，因为这个 job 没有这些服务。MySQL、Redis、Kafka 留给以后的功能 skill，不在这次骨架里。
- 每个新服务使用一个未占用的 `grpc_addr`。不复用 `:9001`、`:9002`、`:9004`、`:8000`、`:8001`、`:8080`。同一次生成的多个服务端口互不相同。从 `:9010` 起分配，跳过已占用端口。本地配置、deploy 配置和 compose 端口映射使用同一个端口。
- 键前缀仍是 `/orbikit/services`。真实部署走 deploy 配置里的 etcd 注册。

启动测试加载本地配置（不填 `etcd.endpoints`）。`discovery.Open` 在未启用时返回 nil registry 和 nil error，`Bind` 为空操作。测试调用五步启动函数，看到监听地址后取消该函数的上下文。不另起一个只等信号的进程。deploy 配置不作为这次监听测试的配置。

CI 的 docker 矩阵保持 `core`、`chatroom`、`gateway`、`webhook`。这个 job 不是新服务的验收门。新服务的验收是 `go test -race ./...` 里的监听测试。compose 仍然写入服务项，方便人启动。

验收时用没有业务含义的服务名 `echo` 走完三步。其中没有礼物、私聊、榜单或玩法。监听测试变绿之后，删除 `echo` 的 `cmd`、`internal`、两份配置、compose 服务项，以及只为 `echo` 生成的 proto 和 `api/gen` 产物。skill 正文不依赖这些文件留在仓库里。以后用户确认的真实服务保留自己的监听测试。

### R3-1 — consistency (blocking)

**Problem**

> 成功标准要求监听测试在 go test -race ./... 中调用五步启动函数，看到监听地址后取消上下文并结束。推荐做法里的启动测试仍写「测试启动进程，观察到监听地址，然后取消上下文」。取消测试中的上下文停不掉另一个只等信号的进程；只有调用该函数时，取消的才是它自己的上下文。两处对同一次监听测试的入口不一致，按前一句实现会回到「等不到取消后结束」。
